# Формат данных

Всё, что инструменты знают об оборудовании, лежит в `catalog/`: формат
`jef-sure/boards`, `format_version` 2. Одна схема, `catalog/format.schema.json`,
описывает все файлы, проверяет их `tools/check_format.py`.

| путь | что там |
|---|---|
| `catalog/boards/<name>/board.json` | плата: её проводка и значения; рядом `sdkconfig.defaults` |
| `catalog/modules/<name>/module.json` | модуль: устройства без платы, проводку задаёт проект |
| `catalog/devices/<family>/device.json` | устройство: роли, адреса, параметры, что умеет сам чип |
| `catalog/libraries/<экосистема>/<владелец>/<имя>/library.json` | библиотека: какие чипы поддерживает, как их запускает, что с ними умеет |
| `catalog/mcu/<target>/mcu.json` | чип: GPIO, хосты и что в нём есть. Делается из ESP-IDF скриптом `tools/make_mcu.py` |
| `catalog/connectors/<type>/connector.json` | тип разъёма: контакты, напряжение |
| `catalog/rules.json` | что делает плату неверной и чего не видит схема |

Имена состоят из строчных латинских букв, цифр и `_`: из них получаются символы Kconfig.

## Как собирается плата

Плата называет устройства каталога и хранит только своё. Инструменты накладывают
слои по JSON Merge Patch (RFC 7386), от общего к частному:

1. устройство каталога;
2. вариант семейства (`"variant": "scd41"`);
3. плата;
4. вариант платы (`"extends": "cyd_s028r"`);
5. «мои для модели», затем проект.

Значение в более позднем слое заменяет прежнее, а `null` удаляет поле. Поэтому
неразведённая линия записывается `"nc"`, а не `null`. Массив заменяется целиком,
поэтому всё, что слой может менять, — объект с именованными записями.

Схема проверяет каждый файл как он написан и ещё раз плату после слияния. Затем
применяется `catalog/rules.json`: одни и те же правила читают `tools/rules.py` в
генераторе и `editor/rules.js` в редакторе.

## Плата

```json
{
    "format": "jef-sure/boards",
    "format_version": 2,
    "kind": "board",
    "name": "jc1060p470c",
    "title": "Guition JC1060P470C",
    "description": "7-inch 1024x600 JD9165 on MIPI-DSI, GT911 touch, ES8311 sound",
    "notes": ["что в ней особенного"],
    "mcu": { "target": "esp32p4", "flash_mb": 16, "psram_mb": 32, "notes": "..." },
    "buses": { "...": "..." },
    "devices": { "...": "..." }
}
```

| поле | значение |
|---|---|
| `name` | имя каталога. Становится `CONFIG_BOARD_SELECT_<NAME>` и именем файла связующего кода |
| `title` | что показывают меню и `board_info()->title` |
| `description` | одно предложение: подсказка в меню и заголовочный комментарий связующего кода |
| `maker`, `part` | кто делает плату и как он её называет, например `JC1060P470C`. У модуля они тоже есть |
| `revision` | ревизия печатной платы, которую описывает файл, как её пишет производитель |
| `price`, `tariff` | цена и таможенный код, см. [Цена](#цена) |
| `notes` | особенности словами, текст или список. Инструменты показывают, но не читают |
| `mcu.target` | каталог в `catalog/mcu/` |
| `mcu.part` | чип, как его называет производитель, например `ESP32-D0WD-V3` |
| `mcu.flash_mb`, `mcu.psram_mb` | для людей; настройки несёт `sdkconfig.defaults` |
| `mcu.revision` | ревизия чипа: её скорости и строки берутся из `catalog/mcu/`, см. [choosing-a-board.md](choosing-a-board.md) |
| `mcu.psram_mhz`, `mcu.cpu_mhz` | частота ниже той, что позволяет ревизия, если плата её ограничивает |
| `mcu.notes` | что задаёт `sdkconfig.defaults` и почему |
| `mcu.controls` | значения параметров чипа, например `wifi_tx_power` |
| `extends` | плата, вариантом которой является эта |
| `power` | линии питания и стробы в порядке запуска, см. [Питание](#питание) |
| `shared_pins` | линии, которыми несколько устройств пользуются намеренно |
| `connectors`, `images`, `checked`, `origin` | см. ниже |

Поля вида `x_*` свободны: инструменты их не читают.

## Линии

Провод записывается везде одинаково:

| форма | значение |
|---|---|
| `21` | GPIO |
| `"nc"` | не разведена |
| `{ "gpio": 0, "active": "low", "pull": "up" }` | GPIO со свойствами |
| `{ "gpio": 4, "analog": [600, 960] }` | читается через АЦП: окно в милливольтах |
| `{ "via": "io", "bit": 3 }` | бит расширителя |
| `{ "via": "pmu", "rail": "dldo1" }` | рейка PMIC |
| `{ "via": "adc", "channel": 2 }` | канал микросхемы АЦП |

Кнопки на резисторной лестнице делят один GPIO. Каждая из них — устройство со своим
окном. Окна могут соприкасаться, но не пересекаться.

## Шины

`buses` — словарь видов, в каждом именованные шины. Имя шины SPI, I2C или I2S — это
хост или порт чипа: `spi.spi2` — его SPI2, `i2c.i2c0` — его I2C0. Программная шина
называется `soft0`.

```json
"buses": {
    "spi":  { "spi2": { "hz": 40000000, "mosi": 13, "miso": 12, "sclk": 14 } },
    "qspi": { "spi2": { "hz": 40000000, "d0": 21, "d1": 48, "d2": 40, "d3": 39, "sclk": 47 } },
    "i2c":  { "i2c0": { "sda": 7, "scl": 8 } },
    "i2s":  { "i2s0": { "mclk": 13, "bclk": 12, "ws": 10, "dout": 9, "din": "nc" } },
    "dsi":  { "dsi0": { "lanes": 2, "lane_mbps": 750, "phy_ldo_chan": 3, "phy_ldo_mv": 2500 } }
}
```

| вид | поля |
|---|---|
| `spi` | `mosi`, `miso`, `sclk`; `hz` необязательно |
| `qspi` | `d0`..`d3`, `sclk`; `hz` необязательно |
| `i2c` | `sda`, `scl`; `hz` необязательно |
| `i2s` | `bclk` и `ws` или `clk` для PDM (`"nc"` у выхода PDM без линии такта, на фильтр); `mclk`, `dout`, `din` необязательны; `dout2`, `din2`..`din4` для дополнительных линий PDM |
| `dsi` | `lanes`, `lane_mbps`, `phy_ldo_chan`, `phy_ldo_mv` |
| `p8` | `d0`..`d7`, `wr`, `dc`, `hz`; `rd` необязательно |
| `rgb` | `pclk`, `data` (список); `de`, `vsync`, `hsync`, `hz` необязательны |
| `csi` | `lanes`; `lane_mbps`, `phy_ldo_chan`, `phy_ldo_mv` необязательны. У линий свои выводы |
| `dvp` | `pclk`, `vsync`, `de`, `data` (от 8 до 16 линий); `hsync` необязательно |
| `uart` | `tx`, `rx`; `rts`, `cts`, `baud` необязательны |

Любой другой вид (`sdio`, `sdspi`) хранится как данные. Программа читает его через
`board_bus_get("sdio.sdio0", "clk", &pin)`.

## Устройства

`devices` — именованные устройства. Под устройством с `chip` лежит запись из
`catalog/devices/`, поэтому плата пишет только отличия:

```json
"sound": {
    "chip": "es8311",
    "on": { "i2c.i2c0": {}, "i2s.i2s0": {} },
    "pins": { "pa": 11 },
    "config": { "sample_rate": 22050, "pa_voltage": 5.0, "codec_dac_voltage": 3.3 },
    "controls": { "volume": { "start": 25 } }
},
"boot": { "class": "button", "pins": { "in": { "gpio": 35, "active": "low" } } }
```

| поле | значение |
|---|---|
| `chip` | каталог в `catalog/devices/`. Деталь без записи, например кнопка, указывает `class` сама |
| `chip_try` | вместо `chip`: какими чипами может оказаться устройство, в порядке проверки при запуске. `class` устройство указывает само |
| `variant` | член семейства |
| `library` | какой библиотекой пользуется устройство; у чипа с одной библиотекой загрузчик подставляет её сам |
| `library_version` | версия библиотеки, если это не та, что описана в записи |
| `needs` | что программе нужно от библиотеки, предметами из её `supports` |
| `firmware_version` | прошивка этого устройства, если она не новейшая из описанных |
| `maker`, `part`, `marking`, `ref`, `draw` | чем устройство является физически, см. [Что стоит на плате](#что-стоит-на-плате) |
| `price`, `tariff`, `count` | для того, что покупается отдельно, см. [Цена](#цена) |
| `class` | роль или список ролей: `display`, `touch`, `audio`, `storage`, `radio`, `network`, `nfc`, `sensor`, `io_expander`, `pmic`, `battery_adc`, `adc`, `camera`, `imu`, `rtc`, `button`, `encoder`, `keyboard`, `gamepad`, `led`, `usb`, `gps`, `motor`, `i2c_mux`, `fuel_gauge`, `other` |
| `on` | шины устройства, у каждой то, что относится к этому подключению: `address`, `address_try`, `cs`, `hz`, `mode`, `role`; `format` у шины I2S (`std`, `tdm`, `pdm`; у двух направлений одного порта он может быть разным); `sio` у шины SPI с данными в обе стороны по MOSI |
| `pins` | остальные линии: `dc`, `rst`, `backlight`, `int`, `te` |
| `config` | факты, которые не меняются |
| `controls` | параметры, см. ниже |
| `provides` | что устройство даёт и с какими характеристиками, см. ниже |
| `start` | `defer` для устройства, молчащего до первого события, `after` для порядка запуска |

Запись каталога пишет `on` по виду, `"i2c": { "address": "0x18" }`, и может отметить
вид как `required`. Канал мультиплексора записывается `i2c.mux.ch0`.

### Дисплей

`config.kind` приходит от чипа: `graphics` или `character`.

```json
"lcd": {
    "chip": "ili9341",
    "on": { "spi.spi2": { "cs": 15 } },
    "pins": { "dc": 2, "rst": "nc", "backlight": { "gpio": 21, "active": "high" } },
    "config": { "primary": true, "panel": { "width": 240, "height": 320, "mm_w": 43, "mm_h": 58 }, "depth_bits": 16 },
    "controls": { "orientation": { "start": { "x": "right-left", "y": "top-bottom", "swap": true } } }
}
```

`panel` — стекло так, как его сканирует контроллер: пиксели и миллиметры в одном
направлении. Миллиметры необязательны, но указываются только вместе: без них
`board_display.mm_w` и `mm_h` равны 0. `orientation` — как его показывает плата. `swap` истинно, когда ось x
дисплея идёт вдоль столбцов стекла. `primary` отмечает основной дисплей.
У символьного дисплея есть `config.geometry`, например `"20x4"`.

`config.timing` нужен панели, которую кормят непрерывно, RGB или видеорежим MIPI-DSI:
`pclk_hz`, `hsync_pulse`, `hsync_back`, `hsync_front`, `vsync_pulse`, `vsync_back`,
`vsync_front` и необязательные `pclk_edge`, `hsync_active`, `vsync_active`,
`de_active`. Откуда взяты числа, говорит `checked`: цифры производителя остаются
подсказкой, пока не измерены на плате.

Дисплеи, показанные как один экран, — это группа. `side_by_side` означает
`dgx_vscreen_2h_init(left, right)`: ширина складывается, высота берётся большая, глубина
цвета у обоих должна быть одна. Шина и ориентация у каждого свои:

```json
"display_groups": { "wide": { "how": "side_by_side", "left": "left", "right": "right", "primary": true } }
```

### Тач

`config.over` называет дисплей, над которым лежит тач, или `"none"`. Генератору
нужен дисплей: `"none"` ждёт поддержки в DGX-DI. `x_max` и `y_max` — наибольшие
сырые координаты, а не их число; у калибровки должны быть те же значения и размер
панели. См. [calibration.md](calibration.md). `fingers` берётся из записи чипа, плата
пишет его, только если значение отличается.

### Звук

| чип | что это |
|---|---|
| `es8311` | кодек на I2C и I2S; `pins.pa` включает его усилитель; `controls.volume` |
| `esp32_dac` | собственный ЦАП ESP32, `pins.out` на GPIO 25 или 26 |
| `i2s_amp` | усилитель на I2S без кодека и без громкости: сэмплы масштабирует программа |

Сэмплы во всех случаях 16-битные, моно. `config.clock` говорит, откуда кодек берёт
такт: `mclk` или `bclk`, если он получает его из тактов битов.

### Камера

Устройство класса `camera`: сенсор на шине для картинки и обычно на I2C для регистров.
У платы может быть разъём без сенсора, тогда она называет только шину и разъём. Сенсор
на шлейфе — это модуль:

```json
"buses": { "csi": { "csi0": { "lanes": 2, "phy_ldo_chan": 3, "phy_ldo_mv": 2500 } } },
"modules": { "camera": { "module": "ov02c10_csi", "on": { "csi.csi0": {}, "i2c.i2c0": {} } } }
```

У параллельной камеры `xclk`, `rst` и `pwdn` лежат в `pins`, а `config.xclk_hz` указан,
если такт даёт плата. `chip` может отсутствовать: импортированная плата часто не
называет сенсор. `chip_try` перечисляет те, что надо попробовать. Запись сенсора
указывает `provides.camera`: `width_max`, `height_max`, `formats`. Режимы, которые есть
у библиотеки, лежат в её `supports.modes`. Связующий код камеру пока не запускает, она
хранится как данные.

### SD

Устройство класса `storage` на шине SPI, его `cs` в `on`. Если хоста для него не
осталось, как на CYD S028R, его шина имеет вид, который компонент не настраивает:
`sdspi`.

### Батарея

Устройство класса `battery_adc`, которое читается через делитель:

```json
"battery": { "class": "battery_adc", "pins": { "in": 5 }, "config": { "divider": { "top_ohm": 33000, "bottom_ohm": 100000 } } }
```

От батареи до АЦП стоит `top_ohm`, от АЦП до земли `bottom_ohm`. `switch` — линия,
которая подаёт питание на делитель только на время чтения, `settle_us` — пауза после
неё. Владелец у этой линии такой же, как у любой другой.

### Что стоит на плате

Устройство говорит, чем оно является физически: `maker`, `part`, `ref` как на схеме и
`marking`, если на корпусе можно прочитать только это. `maker`, `part` и `compat` даёт
запись чипа, а плата пишет `part`, если знает больше, например `ES8311-S`. Семейство
указывает `part` и `compat` в каждом варианте. `maker` — наше короткое имя, `compat` —
compatible из devicetree, единственное поле для внешнего формата.

Деталь, которую не видит программа, это устройство класса `other` без `on`:

```json
"reg_esp": { "class": "other", "ref": "U7", "part": "AMS1117-3.3" }
```

`draw` задаёт ток по режимам в мА, здесь или в записи чипа, а `mcu.draw` делает то же
для чипа платы:

```json
"draw": { "active": { "ma": 80, "ma_peak": 500 }, "sleep": { "ma": 1 } }
```

Пустое место на плате описывается в `notes`.

## Питание

`power` перечисляет линии питания и стробы в порядке запуска. Шаг берёт питание только
от шага перед ним, поэтому петли в списке быть не может.

```json
"power": [
    { "name": "USB", "source": "usb", "mv": 5000 },
    { "name": "VIN", "source": "vin" },
    { "name": "5V", "from": [{ "name": "USB", "through": "d_usb" }, { "name": "VIN", "through": "q_vin" }] },
    { "name": "3V3", "from": "5V", "through": "reg_tft", "regulator": "ldo", "mv": 3300, "ma_max": 1000, "dropout_mv": 1300, "feeds": ["lcd", "touch"] },
    { "name": "PERIPH", "from": "3V3", "line": 10, "level": 1, "delay_ms": 100, "feeds": ["keyboard"] },
    { "line": 39, "level": 1, "why": "CS of the SD card, before the bus starts" }
]
```

| поле | значение |
|---|---|
| `name` | как на схеме или на плате. Контакт разъёма с таким текстом и есть эта линия |
| `source` | откуда приходит питание: `usb`, `vin`, `battery` или `connector` у модуля, которого питает плата |
| `from` | шаг, от которого питается линия, или список входов: имена либо объекты с `name`, `through`, `dropout_mv` |
| `through` | устройство на пути, или список по порядку. При списке в `from` оно стоит после пути каждого входа |
| `regulator` | `ldo` пропускает ток как есть; `buck`, `boost` и `charger` преобразуют мощность, и токи по обе стороны разные |
| `efficiency_percent` | КПД преобразователя |
| `line`, `level`, `delay_ms` | чем линия включается, или рейка PMIC; уровень включения; пауза после него |
| `mv`, `ma_max` | напряжение и наибольший ток |
| `dropout_mv` | сколько теряется от входа к выходу: минимум для `ldo`, падение на диоде |
| `feeds` | устройства, `mcu` или шаг модуля в виде `<use>_<name>`. Чип на двух линиях указан в обеих |
| `why` | что это за шаг, словами |

Шаг с именем — это линия питания, и она владеет своим GPIO. Шаг без имени — строб на
линии, которой владеет устройство. Линия, которой устройство уже владеет, остаётся у
него, а `why` об этом говорит: на JC1060P470C повышающий преобразователь подсветки
включается линией подсветки дисплея.

Список — один массив, поэтому слой заменяет его целиком. Слою, который убирает
устройство через `null`, новый список не нужен: устройство исчезает из `feeds` само.
Шаги модуля идут после шагов платы и получают имена `<use>_<name>`.

## Параметры

В `controls` лежит то, что может отличаться от состояния устройства при старте:

```json
"controls": {
    "volume": { "how": "codec_volume", "min": 0, "max": 100, "read": "command", "start": 25 },
    "interface": { "how": "switch", "lines": ["I0", "I1"], "values": { "i2c": [1, 0], "spi": [0, 1] }, "read": "none" }
}
```

`how` говорит, чем параметр задаётся, из закрытого списка; для того, что задаёт
программа, это одна функция на C в адаптере библиотеки. `switch`, `solder` и `derived` — для
человека или для инструментов. `read` говорит, как узнать значение: `command`,
`probe` или `none`. `start` — значение платы. Значение, которое хочет человек, лежит
в более позднем слое и проверяется по `min`, `max` и `values`.

В `shared_pins` линия может быть общей только при определённом значении параметра:

```json
"boot_te": { "line": 0, "devices": ["lcd", "boot"], "only_while": { "device": "lcd", "control": "te", "value": "off" } }
```

## Что устройство даёт

```json
"provides": {
    "co2": { "unit": "ppm", "output": [0, 40000], "specified": [400, 5000],
             "accuracy": [{ "from": 400, "to": 1000, "plus_minus": 50, "percent": 2.5 }] }
}
```

`output` — что устройство может выдать, `specified` — где производитель обещает
точность. Другие характеристики зависят от вида, например `standards`, `targets_max`,
`tx_ma_max` и `range_mm` у считывателя NFC. Число лежит там, что его задаёт: предел чипа
здесь, предел библиотеки в её записи, см. [Библиотеки](#библиотеки).

Антенна не принадлежит чипу: её
называет модуль или плата в `antenna` (`kind`: `on_board`, `connector`, `wire`) и там же
хранит её характеристики, с записью в `checked` о том, кто измерил. Большая антенна на том
же чипе — это другой модуль. Семейство пишет общее, а записи `variants` накладывают остальное.
`variant_by` говорит, чем задан вариант и как программа может его узнать.

## Библиотеки

Устройство описывает, что умеет чип, библиотека — что она делает с этим чипом. Запись
лежит в `catalog/libraries/<экосистема>/<владелец>/<имя>/library.json`, чип о своих
библиотеках не знает, а имя библиотеки на плате — это её путь: `esp-idf/jef-sure/pn5180`.

```json
{
    "kind": "library", "ecosystem": "esp-idf", "owner": "jef-sure", "name": "pn5180",
    "install": [{ "via": "registry" }, { "via": "git", "url": "https://github.com/jef-sure/esp32-component-pn5180.git", "ref": "v{version}" }],
    "transports": {
        "spi": { "init": { "call": "pn5180_spi_init", "args": ["{host}", "{sclk}", "{miso}", "{mosi}", "{hz}"], "returns": "bus" },
                 "shared": { "call": "pn5180_spi_attach", "args": ["{host}", "{hz}"], "returns": "bus" } }
    },
    "chips": {
        "pn5180": {
            "header": "pn5180.h", "on": ["spi"],
            "init": [{ "call": "pn5180_init", "args": ["{bus}", "{cs}", "{busy}", "{rst}"], "returns": "nfc", "ok": { "not": "NULL" } }],
            "setup": [{ "call": "pn5180_14443_init", "args": ["{nfc}"], "returns": "protocol", "for": "iso14443a" }],
            "standards": ["iso14443a", "iso15693"], "modes": ["reader"],
            "supports": { "mifare_classic": ["uid", "blocks_write", "ndef_read"] },
            "limits": { "iso14443a_cards_per_scan": 14 }
        }
    },
    "versions": {
        "0.0.2": { "frameworks": { "esp-idf": ">=5.3.0" }, "requires": { "esp-idf/jef-sure/dgx": "^0.10.2" } },
        "0.0.1": { "frameworks": { "esp-idf": ">=5.3.0" }, "requires": { "esp-idf/jef-sure/dgx": "^0.10.1" } }
    },
    "history": [
        { "before": "0.9.3", "chips": { "st77916": null } },
        { "before": "0.9.0", "chips": { "st7789": { "init": [{ "call": "dgx_st7789_init", "args": ["{bus}", "{rst}", "{depth}", "{color}"] }] } } },
        { "before": "0.5.0", "chips": { "jd9165": null } }
    ]
}
```

В `chips` по каждому поддерживаемому чипу отдельно: заголовок, шины (`on`), символы Kconfig
(`select`), запуск (`init`), начальная настройка по порядку (`setup`), вызовы для параметров
(`controls`) и возможности (`standards`, `modes`, `supports`, `limits`). `{имя}` в `args` —
значение, которое подставляет вызывающий, остальное попадает в вызов как есть. Шаг — это
`call`, применение параметра `control` или установка линии `line`: шаг `"line": "backlight"`
значит, что драйвер не зажигает подсветку сам. `transports` говорит, как библиотека
поднимает шину: `init` создаёт её, `shared` садится на уже поднятую.

Операции, которой нет в `supports`, библиотека не делает:
`"mifare_classic": ["uid", "ndef_read"]` значит, что библиотека читает NDEF с такой карты, но
не пишет. Если программе это нужно, она говорит об этом в `needs`, и правило
`library_does_what_is_needed` отказывает плате, чья библиотека этого не делает:

```json
"nfc": { "chip": "pn5180", "library": "esp-idf/jef-sure/pn5180", "needs": { "mifare_classic": ["ndef_write"] } }
```

`license` — лицензия описанной версии, выражением SPDX, если оно есть, а шаг `history` говорит,
когда лицензия была другой. Для экосистемы `esp-idf` её заполняет из реестра
`tools/sync_versions.py`; `Custom` реестр пишет для собственного текста лицензии.

`ecosystem` говорит, где библиотека опубликована: от него зависят реестр и имя. С чем
собирается её код, говорит `frameworks` в каждой версии: `{ "esp-idf": ">=5.2.0" }`. Это разные
вещи: библиотека из реестра Arduino может собираться и с `arduino-esp32`, и с `esp-idf`, и тогда
у неё два ключа. Оба поля открыты: новая экосистема — новый каталог в `catalog/libraries/`, а
схема остаётся прежней. `targets` перечисляет чипы, если библиотека их ограничивает; отсутствие
списка значит только, что она этого не объявила.

`install` перечисляет способы получить библиотеку, от предпочтительного: `registry` (реестр её
экосистемы), `git` (`url`, `path` внутри репозитория и `ref`: тег с `{version}` или ветка),
`archive` (`url`) и `platform` (она идёт вместе с фреймворком). Манифест компонента берёт первый
способ. Если версия есть не у всех способов, её запись называет их в `via`: так помечается версия,
которая есть только в тегах git.

Шаг с `call` обязан сказать, как понять, что вызов удался: поле `ok` следует соглашениям самой
библиотеки. `{ "not": "NULL" }` для указателя, `{ "equals": "ESP_OK" }` для ESP-IDF,
`{ "equals": "ESP_CODEC_DEV_OK" }` для кодека, `"none"` для вызова без результата.

`versions` хранит каждую версию отдельно: `frameworks`, `targets` и другие библиотеки, которые
ей нужны (`requires`). Для экосистемы `esp-idf` эти записи заполняет из реестра
`tools/sync_versions.py`.

Запись описывает одну версию, она названа в `described`, и всё сказанное в записи верно именно
для неё. `history` говорит, чем отличались более старые: поля шага (`chips`, `transports`,
`interfaces`, `groups`, `values`) — поправки Merge Patch для всех версий раньше `before`, `null`
убирает. Так записывается всё, что менялось: чипы, шины, возможности и аргументы вызовов. Когда
в новой версии появилась возможность, в `chips` она дописывается, `described`
меняется, а в `history` добавляется шаг без неё. Устройство, которое держится за старую версию,
называет её в `library_version`, и правила проверяют `library` и `needs` по этой версии, а отказ
называет версию: `esp-idf/jef-sure/pn5180 0.6.0 does not do ndef_write of mifare_classic`. Версия
новее `described` отвергается: про неё каталог ничего не знает. `tools/sync_versions.py` сообщает,
когда в реестре появилась версия новее описанной.

`adapter` говорит, как библиотеку берёт этот компонент: версия, под которую написан его код,
символ правила манифеста, компоненты сборки и файлы в `adapters/<владелец>__<имя>/`: что
подключает клей (`headers`), что подключает программа (`public`) и что компилируется по какому
символу (`sources`). Запись без `adapter` — описание: чип с такой
библиотекой остаётся в данных, а компонент его не запускает, как PN532 на терминале.

Требование библиотеки — поле самой библиотеки, поэтому у DGX-LVGL нет чипов, а записи
версий есть.

## Прошивка

Прошивка внутри устройства тоже меняет его возможности, поэтому у файла устройства есть блок
`firmware`:

```json
"firmware": {
    "read": "command", "scheme": "hex", "described": "3.A",
    "history": [{ "before": "3.A", "controls": { "lpcd_reference": null } }]
}
```

`kept` говорит, где она живёт (`none`: хост записывает её при каждом старте), `set` — кто её
ставит, `read` — как программа узнаёт версию. Номер версии хранится так, как его пишет
производитель, а `scheme` говорит, как его сравнивать: при `hex` части номера шестнадцатеричные,
и `3.A` новее `3.9`. Предварительный выпуск младше своего выпуска, `1.2.0~3` новее `1.2.0`, а
`1.0` равно `1.0.0`. `described` и `history` устроены как у библиотеки:
файл описывает одну версию, а шаги поправляют `config`, `controls` и `provides` для более старых.
Устройство называет свою в `firmware_version`; слой прошивки ложится после варианта семейства и
раньше платы. Какую прошивку принимает библиотека, говорит поле `firmware` у чипа в её записи.

## Разъёмы и картинки

```json
"connectors": { "P3": { "type": "HC 1.25 mm, 4 pins", "pins": [21, 22, 35, "GND"],
                        "at": { "image": "front", "x": 0.82, "y": 0.1 } } },
"images": { "front": { "file": "front.webp", "source": "own", "shows": "front", "up": { "x": 0, "y": -1 } } }
```

В разъёме число — это GPIO, строка — питание или сигнал без GPIO; строка, равная
`name` шага `power`, и есть эта линия. Разъём повторяет пины, которыми владеют
устройства, поэтому их владельцем не считается.

Разъём, контакты которого заданы стандартом, называет свою запись в `of`, и `type` ему
не нужен:

```json
"J1": { "of": "stemma_qt", "pins": ["GND", "3V3", 8, 9] }
```

`catalog/connectors/<тип>/connector.json` хранит `pitch_mm`, `volts` и `pins`: что идёт
по каждому контакту, начиная с первого. Плата указывает столько же контактов. `images` может
стоять в любом файле каталога, сам файл лежит рядом с JSON; `source` обязателен,
чужие фото не копируются. `at` ставит метку в долях картинки, а `up` показывает, куда
смотрит верх экрана.

## Цена

`price` может быть у платы, модуля и устройства. Это именованные предложения, чтобы слой мог
добавить своё: например, проект записывает, сколько заплатил на самом деле.

```json
"price": {
    "amazon": {"shop": "Amazon", "currency": "EUR", "range": [6, 6], "date": "2026-10-31", "source": "from memory"},
    "aliexpress": {"shop": "AliExpress", "currency": "EUR", "range": [0, 3], "date": "2026-10-31", "source": "from memory"}
}
```

| поле | что |
|---|---|
| `shop` | где продаётся |
| `currency` | код валюты, например `EUR` |
| `range` | наименьшая и наибольшая цена за штуку, никогда одно число. «Меньше 3» записывается как `[0, 3]` |
| `qty` | с какого количества действует цена, без поля 1. Несколько предложений одного магазина дают цены по партиям |
| `date`, `source` | когда цена замечена и кто её назвал: цена устаревает |
| `notes` | всё остальное |

Доставки и пошлины здесь нет: они зависят от всего заказа, а не от одной платы. См.
[board_bom.py](tools.md#board_bompy).

`tariff` — таможенный код товара, HS или CN, только цифры: по нему считаются сборы с мелких
посылок. `count` у устройства говорит, сколько его идёт на одно изделие, для того, у чего нет
своего подключения: винты, кабели.

## Откуда взяты факты

`origin` говорит, откуда импортирован файл. `checked` говорит, на чём стоят его
факты. Это два разных вопроса.

```json
"origin": { "from": "rzeldent/platformio-espressif32-sunton", "ref": "a96fa42", "license": "GPL-3.0", "date": "2026-10-30" },
"checked": {
    "pins": { "level": "schematic", "source": "JC1060P470C_I_W_Y-V1.0.pdf", "date": "2026-10-28" },
    "touch": { "level": "hardware", "covers": ["devices.touch"], "by": "Anton", "date": "2026-10-30" },
    "sound": { "level": "schematic", "covers": ["devices.sound"], "result": "pending" }
}
```

Уровни от самого надёжного: `hardware`, `schematic`, `datasheet`, `vendor-docs`,
`vendor-code`, `community`, `extracted`, `unchecked`. `covers` говорит, к чему
относится запись, без него она про весь файл. `result` по умолчанию `confirmed`,
`pending` значит, что ещё предстоит проверить, `refuted` — что источник расходится.
`unit` говорит, на каком экземпляре проверено. Вариант наследует записи базовой платы с пометкой `on_board`, потому что они получены
на другой плате.

## Что отвергается

Сверх схемы, по `catalog/rules.json`: шина, которой нет на плате; нет шины вида,
который устройство требует; линия через устройство, которое её не даёт; тач над тем,
что не является дисплеем; два тача над одним дисплеем; два основных дисплея; два
владельца GPIO, бита расширителя или адреса I2C; пересекающиеся окна лестницы; один
хост, названный и `spi`, и `qspi`; калибровка для другого диапазона или размера дисплея; значение вне того, что
принимает параметр; GPIO, которого нет у чипа; выход на линии только для входа; имя в
`shared_pins`, `power`, `start` или `checked`, которого не существует; два шага
`power` с одним именем; шаг, который берёт питание не от шага перед ним; разъём, чьи
контакты не совпадают с его записью.

`tools/boards_gen.py` отвергает ещё и то, для чего не может сделать связующий код.
Формат описывает больше, чем генератор пока настраивает, и ошибка называет устройство
и то, чего не хватает: `chip_try`, `config.timing`, `clock` со значением `bclk`, формат
I2S кроме `std`, `sio`, кнопка на лестнице, тач, чип которого не указывает `fingers`,
шаг `power` с `line`. Запускаются только дисплеи, тачи, звук и кнопки, остальные устройства хранятся как
данные.
