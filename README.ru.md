# boards

*[In English: README.md](README.md)*

Программа для ESP-IDF пишется один раз, а плата выбирается при сборке: плата каталога, своя плата или окно на
компьютере с дисплеем выбранной платы. Компонент настраивает дисплей, тач, звук, радио, кнопки и шины этой платы;
программа запрашивает части **по типу**, а не по имени платы:

```c
#include "boards.h"
#include "boards_dgx.h"
#include "boards_dgx_di.h"

board_display_t display = {0};
if (board_display_init(&display)) {
    /* display.width, display.height: 1024x600 or 320x240, whatever the chosen board has;
       display.mm_w, display.mm_h: its size in millimetres */
    dgx_screen_t *screen = board_dgx_screen(&display);
}

board_touch_t touch;
if (board_touch_start(&display, &touch)) {
    /* the touch panel under that display, calibrated by the board's data */
    dgx_di_pointer_t *pointer = board_dgx_di_pointer(&touch);
}
```

Каждая функция `boards.h` есть на каждой плате; для части, которой у платы нет, она возвращает `false`, и программа идёт
дальше без неё. Дескрипторы библиотек (DGX, DGX-DI, hd44780) дают заголовки их адаптеров, см. [API](docs/ru/api.md).

Когда в проекте меняется плата, программа остаётся прежней: новую плату выбирает одна команда, а программе остаётся
самое большее подстроиться под то, чем отличаются данные, — размер дисплея или часть, которой у новой платы нет. Когда
уточняется факт о плате или библиотека меняет то, как запускаются её части, правка идёт в данные и в компонент, а не в
программу. Так устроены [рукописные часы](https://github.com/jef-sure/handwritten-clock): один код для CYD S028R
(ESP32, 320x240 по SPI), 7-дюймовой JC1060P470C и 10,1-дюймовой JC8012P4A1C (ESP32-P4, MIPI-DSI). Плату часы
называют только в одном месте, и причина не техническая: производитель не даёт лицензии на распространение прошивки
тача 10,1-дюймовой платы, поэтому её встраивает сама программа для этой платы. Когда в
0.2.0 компонент взял на себя радио рядом с ESP32-P4, из часов ушёл их собственный код для него.

Плата описана **один раз, как данные**, и у каждого факта указано, откуда он: схема, производитель, измерение на плате.
Всё остальное получается из этого описания: код, который запускает части, конфигурация, зависимости, которые скачивает
сборка, карта пинов и подбор платы под устройство.

[Редактор](#редактор) сокращает путь от замысла до работы над ним. Он берёт то, что нужно устройству, — дисплей,
считыватель, датчик, — и даёт комплекты: платы и модули, которые это делают, с проводами, уровнями и ценами, и
библиотеки, которые с ними работают, — лучшее из доступного, включая то, что уже есть под рукой. Затем он пишет
проект.

## Быстрый старт

Нужен ESP-IDF 6, активированный в терминале, а для окна на компьютере — Linux с SDL2. На Windows есть два пути, пока
не проверенные:

- **WSL2**: ESP-IDF в Linux-дистрибутиве WSL2; окно показывает WSLg; для прошивки плату передаёт в WSL
  `usbipd attach --wsl`.
- **Devcontainer**: образ ESP-IDF с SDL2; окно — через WSLg, подключённый в контейнер (`/tmp/.X11-unix`,
  `/mnt/wslg`); прошивка — через RFC2217 (`esp_rfc2217_server` на Windows), который шаг радио плат на ESP32-P4 пока не
  принимает.

```sh
compote project create-from-example -p my_project jef-sure/boards:hello
cd my_project
idf.py reconfigure
python3 managed_components/jef-sure__boards/tools/board_select.py host --as cyd_s028r .
idf.py build && build/host_cyd_s028r/hello.elf
idf.py --preset cyd_s028r build flash monitor
```

`board_select.py host --as cyd_s028r` даёт проекту две платы: CYD и компьютер, который показывает её дисплей в окне.
Первая сборка — компьютер: окно с дисплеем CYD, тач — мышь. Последняя строка собирает и прошивает саму CYD. Для другой
платы подставьте её имя из [таблицы](#платы); подобрать плату под устройство помогает [редактор](#редактор).

Весь путь — в VS Code, с выбором платы в редакторе, своей программой и тем, что может пойти не так, — в
[Начале работы](docs/ru/getting-started.md).

## Три слова

- **Компьютер** — сборка той же программы для Linux, под цель `linux` ESP-IDF. DGX показывает в окне SDL2 дисплей
  выбранной платы, в его размере и повёрнутым так, как плату держат; мышь — тач, клавиши — кнопки платы, NVS лежит в
  файле `build/host_<плата>/flash.bin`. Это плата `host_<плата>`, её даёт `board_select.py host --as <плата>`: программу
  отлаживают в окне, а потом без изменений собирают и прошивают на плату.
- **Плата программы** — плата, описанная в самой программе, в `components/local-boards/`: плата каталога с модулями,
  которые к ней подключили, или своя плата. Редактор называет её `<проект>_<плата>`.
- **Редактор** — веб-страница компонента (`editor/`): на его холст кладут то, что нужно устройству, а он подбирает
  платы и модули и пишет проект, см. [ниже](#редактор).

## Что может быть у платы

Сам по себе компонент не знает никакого дисплея: у платы его может не быть, а дисплей — одна периферия среди прочих:

- **графический дисплей** под управлением [DGX](https://github.com/jef-sure/esp32-component-dgx):
  панели MIPI-DSI, QSPI или SPI, с их размером в пикселях и в миллиметрах и
  тем, как они лежат на плате;
- **символьный дисплей** (HD44780) через
  [hd44780](https://github.com/jef-sure/esp32-component-hd44780), на плате
  или как модуль: 2004 на переходнике PCF8574 по I2C или голый по GPIO;
- **тач-панель** как устройство [DGX-DI](https://github.com/jef-sure/esp32-component-dgx-di),
  с калибровкой, измеренной на плате и хранящейся в данных;
- **LVGL** через [DGX-LVGL](https://github.com/jef-sure/esp32-component-dgx-lvgl):
  дисплей и тач-панель, которые настраивает компонент, становятся дисплеем и
  устройством ввода LVGL, см. [examples/hello_lvgl](examples/hello_lvgl);
- **звук**: кодек ES8311 на I2S, усилитель на I2S или собственный ЦАП ESP32;
- **радио** рядом с чипом: ESP32-C6 двух плат на ESP32-P4, связь с ней через esp_hosted. Запускает его
  `board_radio_start()`, а шаг прошивки приводит его прошивку к esp_hosted сборки и ничего из неё не хранит на флеше
  платы, см. [радио](docs/ru/radio.md);
- **Ethernet**: IP101 рядом с MAC у ESP32-P4-ETH, ESP32-P4-POE-ETH и JC1060P470C. Запускает его
  `board_ethernet_start()` вместе с интерфейсом esp_netif, см. [API](docs/ru/api.md#ethernet);
- **камера**, пока как данные: её шина, разъём и сенсор описаны, компонент её не запускает;
- **кнопка**; и любая **шина**, которую плата разводит, даже та, которую
  компонент сам не настраивает (SDIO радиомодуля, пины слота SD), хранящаяся
  как данные, которые программа может прочитать.

## Выбор платы

Плата называется один раз, в одной командной строке. `tools/board_select.py` компонента записывает в проект два файла:
`sdkconfig.defaults.<плата>` — настройки чипа, памяти и флеша платы и строку, которая выбирает её в меню конфигурации, —
и `CMakePresets.json`, пресет которого собирает плату в `build/<плата>`. Ни `set-target`, ни `menuconfig`. ESP-IDF 5
пресетов не читает; там плата называется в командной строке:
`idf.py -B build/cyd_s028r -D SDKCONFIG=sdkconfig.cyd_s028r -D BOARD=cyd_s028r build flash monitor`.

Что нужно плате, приходит вместе с выбором: драйверы DGX её панели — как `select`-ы, остальные части (драйвер тача,
кодек, hd44780) — по правилам в `idf_component.yml` компонента, так что сборка для CYD S028R скачивает драйвер XPT2046 и
ничего от GT911 или кодека. **Так условна каждая зависимость компонента, кроме ESP-IDF: сборка скачивает только то, что
нужно выбранной плате. Список зависимостей на странице реестра не отличает условные от безусловных и показывает все: это
то, что может понадобиться всему каталогу, а не то, что скачивает одна сборка.** См.
[что приходит вместе с выбором](docs/ru/choosing-a-board.md#что-приходит-вместе-с-выбором). Смена платы и сборка для
нескольких плат — в [choosing-a-board.md](docs/ru/choosing-a-board.md).

Каждая библиотека приходит диапазоном версий — тех, с которыми собирается её адаптер: менеджер компонентов берёт самую
новую из диапазона, если программа не назвала свою, а клей платы выбирает вызовы по версии, которую взяла сборка. Плата
с частью, которая появилась в библиотеке позже, останавливается на `#error` ниже этой версии. CI собирает каждую плату
с самой старой версией каждого диапазона и с самой новой из каждой более старой линии, см.
[версии](docs/ru/choosing-a-board.md#версии).

## Редактор

Редактор подбирает плату и детали под устройство: роли, которые ему нужны (дисплей, считыватель, датчик), комплекты,
которые подходят, с проводами, уровнями, ценами и тем, что неизвестно; затем он пишет проект. В папке проекта
`python3 managed_components/jef-sure__boards/tools/boards_mcp.py --serve` печатает его ссылку; если отдать сервер агенту
по MCP (`boards_mcp.py --install`), в редакторе появляется ещё и диалог с моделью. См.
[tools.md](docs/ru/tools.md#редактор).

## Чем это отличается от esp-bsp и esp_board_manager

[espressif/esp-bsp](https://github.com/espressif/esp-bsp) описывает собственные платы Espressif вокруг LVGL: каждый
манифест тянет `lvgl` и `esp_lvgl_port`, а дисплей приходит как объект LVGL.
[espressif/esp_board_manager](https://github.com/espressif/esp_board_manager) описывает платы в YAML и генерирует код
инициализации в проект, а плата выбирается через `idf.py bmgr`. Этот компонент задуман для любых плат и любых библиотек.
Сегодня он запускает DGX, DGX-DI и hd44780 своего автора, драйверы Espressif для звука, тач-панелей и радио рядом с
чипом и драйвер XPT2046 от atanisoft. Для остальных частей редактор называет библиотеки, которые программа берёт сама.
Там, где за чип соревнуется библиотека автора, библиотеки этого чипа читаются в аудитах; остальные описаны по их
собственной документации и не проверены. Другие платформы, и среди них Arduino, запланированы. Отличается он тем, как
устроен. Плата — это данные, которые проверяет скрипт: пины, шины, устройства, калибровка, измеренная на плате, и откуда
взят каждый факт; плата программы описывается так же, рядом с программой. Дисплей — одна периферия среди прочих.
Библиотека описана по чипам в `catalog/libraries/`: что она делает с каждым чипом и что требуют её версии, поэтому DGX,
LVGL через DGX-LVGL и другие библиотеки подключаются через адаптеры на одних условиях. Редактор и его решатель подбирают
плату и детали под задачу по этим фактам. Кроме плат каталога из таблицы выше, редактор предлагает платы,
импортированные из других описаний, с пометкой об этом. У esp-bsp он берёт механизм `components/bsp_selector`: один
Kconfig choice, скрытые символы рядом с ним, правила манифеста на них.

## Состояние

Версии и что в них изменилось — в [CHANGES.md](CHANGES.md). CI собирает каждую плату каталога под ESP-IDF 5.5 и 6.1,
каждую плату на более старых версиях, которые берёт диапазон библиотеки (самой старой и самой новой из каждой более
старой линии), и плату программы с дисплеем и 2004: задачи `.github/workflows/build.yml`.

Как проверялась каждая часть, сказано в записях `checked`, у каждой с датой: примеры `examples/hello_board` и
`examples/hello_lvgl` под ESP-IDF 6.1, рукописные часы, перенесённые на компонент, пробы DGX на стенде. Модуль 2004
показывал текст на `esp32_devkit` как на основе платы программы, которая разводит его I2C: плата каталога не открывает
модулю шину. Дисплей-модуль `tft153_st77916` запускался на `esp32s3_devkit` как плата программы, изображение видели.

## Как устроен репозиторий

Для тех, кто меняет сам компонент, а не для программы, которая им пользуется.

```
catalog/boards/<board>/board.json         плата: единственный источник правды
catalog/devices/, catalog/mcu/            что за чипы на ней, лежат под ней
catalog/modules/<module>/module.json      модуль: части на своей маленькой плате, которые программа подключает к плате
catalog/libraries/                        что каждая библиотека делает с каждым чипом и что требуют её версии
catalog/boards/<board>/sdkconfig.defaults что нужно её чипу, памяти и флешу; строки, которые её выбирают
boards/<board>/<board>.c, board.cmake  клей, сгенерированный из данных и закоммиченный
boards/boards.cmake, Kconfig           тоже сгенерированы, как и зависимости в idf_component.yml
include/boards.h                       что программа спрашивает, по роду
src/                                   ядро: board_info, общие I2C и SPI, задача звука, хук прошивки тача
adapters/<владелец>__<имя>/            код под каждую библиотеку, её публичный заголовок в include/
radio/                                 программы шага прошивки: прошивка радио и программа её обновления
tools/resolve.py, rules.py             плата, как её говорят данные, с тем, что она расширяет, и её чипами; движок правил
tools/boards_gen.py                    данные -> клей, Kconfig, списки, правила манифеста, таблицы README
tools/check_format.py                  схема, правила и их случаи в test/format/
tools/check_boards.py                  сгенерированное совпадает с данными; пины не пересекаются; API полон
tools/board_pins.py                    карта пинов платы и её дерево
tools/board_select.py                  выбор плат проекта: их умолчания, пресеты и lock-файлы
tools/board_radio.py                   шаг прошивки, который держит радио рядом с чипом на esp_hosted программы
tools/board_calibration.py             калибровка тача в данные платы, по логу DGX-DI
tools/board_project.py                 новый проект без редактора или комплект редактора, взятый обратно
```

Клей, Kconfig и правила манифеста уже лежат в компоненте: тому, кто берёт его из реестра, ничего генерировать не нужно.
Генератор и проверки нужны только тому, кто меняет данные плат: `tools/check_boards.py` падает в CI, когда то, что лежит
в компоненте, расходится с данными.

### Добавление платы

Скопируйте ближайшую `catalog/boards/<board>/`, отредактируйте `board.json`, напишите её
`sdkconfig.defaults` с причинами в комментариях, запустите
`python3 tools/boards_gen.py --all`, затем `python3 tools/check_boards.py
--host-syntax`. Плата оказывается в меню, в манифесте и в таблице README, и
ни одного из них не нужно трогать. Измерьте тач на плате
(`dgx_di_calibrate_measure` из DGX-DI) и отдайте лог `tools/board_calibration.py`.
См. [docs/ru/adding-a-board.md](docs/ru/adding-a-board.md).
